How Elusion is built

A game on your machine, a server that doesn't believe it.

Elusion is two programs that talk all the time: the game, made in Godot, running on your PC, your phone or in a browser tab, and the server, which keeps everything worth having. This page is how they fit together, who is in charge of what, and how I make sure a player who edits their copy of the game gets nothing for it.

The pieces

What runs where

Six parts, most of them on one small rented server. Each one has a single job.

On your machine

The game

Godot 4.7 and GDScript. The same code builds for Windows and for the browser, where it runs on WebGL 2 with no threads — and on a phone it plays at 30 frames, moves the world 40 times a second and draws its busiest panels once instead of every frame.

The rules

The API

Python and Flask. A small shared core and 39 areas — accounts, saves, the bag, kills and loot, the shop and the smith, trades, parties, guilds, chat, moderation, the minigames — each in its own folder with the same three layers: the route, the rules, the database.

The live world

The presence server

One more Python process, holding every player's live connection. It passes on where everyone stands ten times a second, who leads each area's monsters, attacks, levers and party runs — and keeps its own count of every monster's health.

What lasts

The database

SQLite: one file, in write-ahead mode, backed up every night with its own safe copy. Gold lives in a double-entry ledger, so every coin that exists can be traced to where it came from.

The front door

Caddy

Takes every connection, handles the encryption and renews its own certificates, and sends each request to the right program. The browser version of the game is served from the same address, so it needs no special rules to reach the server.

This page

The website

Plain HTML on Netlify, kept apart from the game's server entirely. The update log, the guide, the Boss Sim and the visit counter all live here.

How they talk

One fight, end to end

  1. You sign in. The game sends your password (or finishes a Google sign-in in your web browser) to the API, and gets back a session. The session is a row on the server: log out, get banned or sign in somewhere else, and that row is gone — every request after it is refused.
  2. You walk into an area. The game asks the API for a short-lived ticket and hands it to the presence server. That server never sees a password: who you are on other players' screens — your name, rank, colour, guild, pets — comes from the server's own records, not from your game.
  3. You fight. One game in each area runs its monsters and says what they do; everyone else's game draws them and sends its hits there. While that happens, the presence server keeps its own books: every hit checked against what your character could actually do, every death judged.
  4. A monster dies. Your game reports the kill. The API pays it only if the server's own count of that fight agrees, rolls the loot itself with a secure random number source, and adds the XP and gold through the ledger.
  5. You pick up the loot. Every item moves one cell at a time, by a request the server carries out. Your game never writes its own bag.

Security

The player's machine is hostile

That is the one sentence the whole server is built on. The attacker I plan for is not a stranger breaking in — that door is shut. It's a real player, logged in properly, running a modified copy of the game. Anything the game works out, they can fake. So the question is never "can somebody get in", it's "how much can a real player lie to the server about what happened?" — and the answer is written down, one rule at a time.

What the server keeps for itself

Level and XP. Gold, through the ledger. Your health, mana and stamina limits, worked out fresh from your class, level and gear every time. Every loot roll. Every bag, bank and worn item. A kill's pay, held to the server's own count of the fight. What a minigame pays, held to its day and to how long the run could really have taken. Even the staff ranks: the owner isn't a row in the database at all, so no request can ever make anyone the owner.

Proof

Every rule names its test

The server's security page lists 47 rules — a ban ends every session on every device at once, two requests sent together can't both spend the same gold, a staff route answers "not found" rather than "forbidden" so the ranks stay hidden, deleting your account takes everything that was yours and nothing that is anybody else's — and every rule ends by naming the exact checks that prove it. A separate test reads the page and fails if any check it names doesn't exist. If the page and the tests ever disagree, the page is wrong.

Behind that: 14,161 automated checks — 7,173 against the server and 6,988 inside a real copy of Godot — a red-team bot that attacks a running server to prove money, items and stats can't be forged, and a self-audit of my own API: twenty-two findings, nineteen closed, two held to a bound and named in the open, and one area audited that turned up nothing.

Honest limits

What isn't solved yet

The security page has a section for what is still open, because a list of only the good news isn't a security model. Two examples. The monsters in an area are run by one player's game, so a modified game can move them strangely on other people's screens — but it can't hurt anyone's health, bag or gold, and their health is the server's count, not its word. And a minigame is played on your machine, so a modified game can claim a better run than it had — up to what the time allows, inside its day. The next step for both is the same: the server running more of the game itself.

Limits, measured

What one small server holds

I'd rather measure than guess. A bot swarm plays the game against a test copy of the server: with 128 players fighting in one area, the live server used about an eighth of one processor core, and with 256 about a quarter. The real limit isn't the processor, it's the network — what has to be sent grows with the square of a crowd in one place — so every game is only sent the players near it, and the server watches its own monthly data and gently tightens itself if a crowd would run past what it can afford.

What comes next

The two halves of the server only share the database, so the live-world process can move to its own machine the day one isn't enough. More writers than SQLite allows would mean Postgres, and nothing before launch needs it. And the big one: the server running more of each fight itself, which the books it keeps today are the first step toward.
